## 一、已完成（前端，已上線）

`報刀_v2.html` 的 `SUB_NOTICE` 物件（搜尋 `訂閱制公告`）：

- 緩衝期內**每天第一次開啟系統**跳一次公告，必須按「我知道了」才關得掉
- 關閉時 POST 到 `/webhook/ack-subscription` 留下已讀紀錄
- 要改日期／價格／額度，**只改 `SUB_NOTICE` 這個物件**，不用動其他地方
  - `id`：換一個新 id ＝ 所有人重新再看到一輪
  - `stopShowingAfter`：過了這天就不再跳（預設 2026-10-31）
- ⚠️ 呼叫點包在 `DOMContentLoaded` 裡是**必要的**，不能改成直接呼叫：`SUB_NOTICE` 是 `const` 且宣告在後面，直接呼叫會踩 TDZ ReferenceError，整段 script 會中斷、整頁功能全掛。

## 三、待建 — Webhook `/webhook/ack-subscription`

前端已經在送這個 request（按下「我知道了」時）：

```json
{
  "token": "...",
  "公告代號": "sub-2026-09",
  "帳號": "derek",
  "姓名": "Derek",
  "確認時間": "2026-09-14 17:17",
  "裝置": "Mozilla/5.0 ..."
}
```

Node 流程：**Webhook（POST, path=`ack-subscription`）→ Google Sheets（Append，目標分頁 `訂閱確認紀錄`）**。

欄位直接對應（比照 `寫入作廢紀錄` node 的寫法）：

```
公告代號 = {{ $json.body['公告代號'] }}
帳號     = {{ $json.body['帳號'] }}
姓名     = {{ $json.body['姓名'] }}
確認時間 = {{ $json.body['確認時間'] }}
裝置     = {{ $json.body['裝置'] }}
```

> 每天按一次就記一筆（不是只記第一次）。重複曝光的紀錄愈多，日後「我不知道要收費」愈站不住腳。
> 不需要 Respond node，前端不等回應。

## 五、待建 — `manual-baodao` 陽春版額度控管

### 為什麼用「送出時間」而不是「手術日期」

額度**必須**以送出時間計算。若按手術日期算，任何人當週用滿後，只要把第 8 筆的日期填成上週就能繞過，上限形同虛設。

好消息：**流水號本身就內含送出當天日期**（`{代碼}{YY}{MM}{DD}{序號}`），已用 969 筆實際資料驗證過（其中 30 筆是補登，流水號日期晚於手術日期，證明兩者確實不同）。所以不用在 `報刀單格式` 加「送出時間」欄位。

### 作法：在既有的讀寫來回裡加計數，不增加任何 Sheets 呼叫

`產生流水號` Code node 已經會讀 `設定` 分頁、也會寫回 `最新流水號`。把 `本週已用`／`本週起始` 一起讀寫即可，**不需要多讀 `報刀單格式`**（多一次 Sheets 讀取就多一個失敗點，就是先前漏刀的成因）。

在 `產生流水號` 的 Code node 裡，**產生新流水號之前**插入：

```js
// ── 陽春版每週額度 ──────────────────────────────
const WEEKLY_CAP = 7;

// 本週一（以送出當下時間為準）
const _now = new Date();
const _day = (_now.getDay() + 6) % 7;            // 週一=0
const _mon = new Date(_now.getTime() - _day * 86400000);
const p2 = n => String(n).padStart(2, '0');
const thisMonday = `${_mon.getFullYear()}-${p2(_mon.getMonth()+1)}-${p2(_mon.getDate())}`;

const plan = String(user['訂閱方案'] || '完整').trim();

if (plan === '停用' || plan === '未訂閱') {
  return [{ json: { success: false, code: 'NOT_SUBSCRIBED', message: '此帳號未訂閱，請聯絡 Ivan' } }];
}

let used = Number(user['本週已用'] || 0);
if (String(user['本週起始'] || '') !== thisMonday) used = 0;   // 跨週歸零

if (plan === '陽春' && used >= WEEKLY_CAP) {
  return [{ json: { success: false, code: 'QUOTA_EXCEEDED', used, cap: WEEKLY_CAP,
                    message: `陽春版每週上限 ${WEEKLY_CAP} 筆，本週額度已用完` } }];
}
```

然後在寫回 `設定` 分頁的 Update node，除了 `最新流水號` 之外多寫兩欄：

```
本週已用 = {{ 上面算出來的 used + 1 }}
本週起始 = {{ thisMonday }}
```

### ⚠️ 關鍵：只有「產生新流水號」時才 +1

一張報刀單有幾個品項，前端就會 POST 幾次，但**只有第一次的 `流水號` 是空的**（後面幾次會帶著第一次回傳的流水號）。額度是「一張單算一筆」，所以計數只能在產生新流水號的那條路徑 +1，帶著既有流水號進來的不能加，否則三個品項的單會吃掉三筆額度。

> 這段要我寫成可直接貼的完整 Code node 的話，把 `manual-baodao` 的 workflow JSON 貼給我。

## 六、待建 — 前端額度顯示與擋單

等 `google-login` 回傳 `訂閱方案` 後再做：

1. 陽春版使用者在 topbar 顯示「本週 5/7」，**進來就看得到剩幾筆**
2. 額度用完時，在按「確認報刀」之前就擋下並顯示升級提示——不能讓人整張單填完才發現不能送
3. `confirmSubmit()` 收到 `QUOTA_EXCEEDED` / `NOT_SUBSCRIBED` 時顯示對應訊息（不是現在的「送出失敗」警示）

> 業務的實際工作流程是：報完刀拿截圖傳群組給內勤 key 進鼎新。所以被擋＝當下就交不出截圖，痛感是即時且在群組裡看得到的——這正是引導升級的機制，但也代表**擋的時機要早、訊息要清楚**，不能讓人以為是系統壞了。

### 為什麼上限訂 7 而不是 5

| 上限 | Derek 每月被擋 | 預估升級 | 月營收 | 淨利（成本 2,000） |
|---|---|---|---|---|
| 5 筆 | 7.2 筆 | 6/6 | 6,000 | +4,000 |
| **7 筆** | 2.1 筆 | 5~6/6 | 5,300~6,000 | **+3,300~4,000** |

純看數字 5 比較好，但**截圖交件**這個工作流程沒有反映在數字裡：被擋的人當下交不出截圖、要在群組裡用不同方式交件，痛感遠大於「月底多打兩行字」。納入這點後 7 也足以驅動升級，且方案看起來比較不像假選項。

### 為什麼不用「平均值」判斷誰適合陽春版

工作量是**陣發性**的。Derek 平均 4.6 件/週看起來完全符合 5 筆上限，但實際週分布是 `0,0,6,6,6,9,2,8`——8 週有 5 週超過 5 筆。用平均值設額度會嚴重低估衝擊。
